# 自動化腳本失敗：先記錄實際狀態再決定是否重試

## 問題

自動化腳本失敗後，Claude 會用同樣的邏輯再試一次——結果當然還是失敗，然後再試，形成無意義的 retry 迴圈。

更糟的是，每次失敗都沒有留下診斷資訊。第三次失敗時，跟第一次失敗的錯誤訊息幾乎一樣，完全沒有縮小問題範圍。

## 原因

Claude 傾向「積極解決問題」，失敗後第一直覺是「再試一次」。但這是人類直覺——程式邏輯不會因為重試就改變，同樣的 input 產生同樣的 output。

## 解決方案

自動化腳本失敗後，強制走診斷流程再決定是否重試：

1. **先記錄實際狀態**：
   - 期望找到什麼（預期值）
   - 實際找到什麼（實際值）
   - 兩者的差異在哪裡
2. **根據診斷決定下一步**：
   - 差異在資料格式 → 修改 parser
   - 差異在路徑 → 修改路徑設定
   - 差異在時序 → 加等待或重新設計流程
3. **才決定是否重試**：確認修改了根因，才執行下一次嘗試

格式範例：
```
[診斷] 期望：/tmp/output/report.pdf 存在
[診斷] 實際：/tmp/output/ 目錄不存在
[根因] 前一步沒有建立目錄
[修復] 加入 mkdir -p /tmp/output/
```

## 可複用的 CLAUDE.md 規則

```markdown
## 自動化腳本失敗 SOP

失敗後禁止用同樣邏輯盲目重試。MUST 先記錄：
- 期望找到/執行什麼
- 實際找到/發生什麼
- 根因是什麼

確認修改了根因，才執行下一次嘗試。

禁止：失敗後立刻重試同樣的操作
```
