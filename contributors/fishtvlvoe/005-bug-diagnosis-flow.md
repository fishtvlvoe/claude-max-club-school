# Bug 修復有正確流程：蒐集→列原因→排除→確定根因→修復→自驗

## 問題

遇到 bug 時，Claude 常常直接開始「猜測」並修改代碼：
- 看到錯誤訊息就改最表面的那行
- 改了沒修好，再改另一行，變成「試試看法」
- 累積多個「試試看」修改，最後讓代碼更難維護
- 修完以後沒有驗證，只說「我改了 X，應該可以了」

這樣的 debug 方式浪費 token，且沒有系統性，同樣的 bug 下次還會出現。

## 原因

Claude 的直覺是快速找到一個可能的解法並嘗試，而不是先花時間建立對問題的完整理解。這在簡單 bug 還行，但遇到稍微複雜的問題就會反覆試錯。

## 解決方案

固定的 Bug 修復 SOP：

1. **蒐集線索**：看完整 error log、stack trace、相關代碼上下文
2. **列出可能原因**：明確說出「可能是 A、B、C 三個原因」
3. **用工具逐一排除**：跑診斷指令、讀相關設定、比較前後版本
4. **確定根因**：說出「根因是 X，因為 Y」，不是「可能是 X」
5. **一次修復**：根據確定的根因，只改需要改的地方
6. **自驗**：修完後自己跑一次確認錯誤消失，不叫用戶跑
7. **才告知**：報告修了什麼、為什麼這樣修

**禁止跳過步驟**，尤其是步驟 3（工具驗證）和步驟 4（確定根因），這是最容易被省略的兩步。

## 可複用的 CLAUDE.md 規則

```markdown
## Bug 診斷 SOP

修 bug 必須走完：蒐集線索 → 列出原因 → 工具排除 → 確定根因 → 一次修復 → 自驗 → 才告知

- 禁止：看到錯誤就直接改、改了說「應該好了」沒驗證
- 禁止：連續多次「試試看」修改而不先確定根因
- 自驗方法：跑相同的指令/請求，確認錯誤訊息消失
```
